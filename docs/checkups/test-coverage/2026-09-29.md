## Needs a human

- **`scripts/validate-plugin.ts:101-107`** — `validateRepository`'s "invalid `plugin.json`" and "plugin name doesn't match its marketplace entry" branches are untested. Closing this cheaply is hard because `validatePlugin` always also runs `validateGenerated` (skills, catalog, task agents, bundles) regardless of whether the manifest itself is valid, so a temp-directory test needs a full, matching generated-files fixture, not just a broken `plugin.json`. Proposal: either (a) short-circuit `validatePlugin` to skip `validateGenerated` when the manifest is invalid (a behavior change — arguably desirable, since generated-file errors are noise once the manifest itself is wrong — so it belongs to a person, not this checkup), or (b) export `validateManifest` for direct unit testing, accepting the slightly wider exported surface. I did not make either change since both are judgment calls the scope reserves for the code-quality/architecture side, not test-coverage.
- **`scripts/bundles.ts:47-49`** — the explicit `if (!result.success) throw new AggregateError(...)` branch appears unreachable with the currently installed Bun (`1.4.2`): I reproduced both a syntax error and an unresolved-import error in a temporary plugin directory, and in both cases `Bun.build` itself threw an `AggregateError` synchronously (message `"Bundle failed"`) instead of resolving with `{ success: false, logs }`. If that's accurate for the Bun version this project targets, the branch is dead code (harmless, but worth a comment or removal), and the error message users would actually see on a bundling failure is Bun's own `"Bundle failed"`, not `"bundling the plugin scripts failed"`. I did not change this because it needs someone to confirm the behavior is stable across the Bun versions the project supports, and decide whether to keep, comment or remove the branch — that's a design call, not a test-coverage fix. No working test exists that reaches this branch.

## About this checkup

- The scope's step 1 ("public functions without tests") is easy to check by pairing `*.ts` files with `*.test.ts` files, but `bun test --coverage`'s numbers are misleading for this repository specifically: several scripts (`checkups.ts`, `doctest.ts`, `session-start.ts`, and now `validate-plugin.ts`) deliberately test their CLI entry point (`main()`) by spawning the script with `Bun.spawn` in a subprocess — which is the right way to test a `process.exitCode`/stdout-based CLI, and matches this project's own established pattern. But Bun's coverage instrumentation doesn't propagate into spawned subprocesses, so those lines show as 0% covered even though they're exercised by a real, passing test. The same applies to TSDoc `@example`s, which run under a separate `bun run doctest` invocation and aren't counted by `bun test --coverage` either (e.g. `lib/files.ts:89-92,131-132` and `lib/interrupt.ts` are fully exercised by examples/subprocess tests but show as uncovered). It would help future runs of this checkup if the scope said explicitly to read the coverage report together with CLI/doctest tests before concluding a line is "untested," rather than only running `bun test --coverage` at face value.
- Otherwise the scope and protocol were clear and easy to follow.
