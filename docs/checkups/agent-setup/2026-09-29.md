## Needs a human

- **Trim the owner's global `~/.claude/CLAUDE.md`.** Its "Code style", "React & UI" and "Testing" sections, plus "Other instructions" (unit tests), are now fully covered by the factory plugin's `conventions/core.md` and `code-react`/`code-testing` skills, injected automatically wherever the plugin is installed. Concrete proposal: keep `~/.claude/CLAUDE.md` only for things the plugin doesn't cover (right now that's nothing code-style-related — it could shrink to just the `@RTK.md` import, or be dropped entirely if RTK is handled another way), and rely on the plugin elsewhere. One caveat worth the owner's own judgment: if `~/.claude/CLAUDE.md` is meant to apply in *other* projects that don't have the factory plugin installed, trimming it would leave those projects without these conventions — the owner may want to keep it as a fallback, or install the plugin more broadly instead. This can't be fixed from here: it's outside the repo, and the checkup's own rules forbid editing anything outside it.
- **Consider marking `security` (and possibly `outdated-packages`) as `priority: true`** in `docs/checkups/checkups.json`, so a genuinely due security check gets the firm "offer to run before other work" nudge instead of blending into the soft due-list line with `retro` and `todos`. This is an editorial call the checkup protocol reserves for the owner (`checkup` skill: "Never change `intervalDays` or `priority` unless the user asks").

## About this checkup

- The skill's scope (item 3) asks to check "`.claude/settings.json`" specifically; this repository has none, only the plugin's own `hooks/hooks.json`. Worth clarifying in the skill whether an absent `.claude/settings.json` should be reported as "not checked" (as done here) or explicitly confirmed as "correctly absent" — the current wording doesn't say what to do when the file simply doesn't exist.
- Item 4 mentions "missing [checkups] (see the runner's suggestions)", but the runner's suggestion step (`checkup` skill, step 2) is a live, in-session judgment call, not a stored or scriptable output — there's nothing to "see" outside of redoing that judgment call yourself, which is what this run did. A pointer to what that judgment should weigh (as the `checkup` skill itself lists: UI presence, production data, user content, public site) would make this instruction self-contained.
- Otherwise the scope and protocol were clear and easy to follow as written.
