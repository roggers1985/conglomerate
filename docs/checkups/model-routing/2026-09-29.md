# Checkup: model-routing (2026-09-29)

Model: Sonnet 5 (session), run as a subagent per the `checkup` task route (sonnet/high)
Previous report: none (first run)

## Summary

`plugins/factory/models.json` and `plugins/factory/scripts/models.ts` still match what Claude Code and the Claude API accept today: the four model aliases (`opus`, `sonnet`, `haiku`, `fable`) and all five effort levels (`low`…`max`) are still valid, and none of the routed task types point at a deprecated or retiring model. The one real mismatch: `code-small` routes to `haiku` with `effort: "low"`, but Claude Haiku 4.5 does not support the `effort` parameter at all — this is a known, ADR-0014-anticipated no-op, not a bug. On `fable`, the primary sources give a direct, citable answer to the open TODO item ("decide whether and where to use fable"): Anthropic positions it as an escalation model ("demanding reasoning and long-horizon agentic work, or when your evals on Claude Opus 5.5 at higher effort still fall short"), not a default for any workload — so the recommendation is to leave it unassigned in `models.json` and instead make explicit that it is the intended target of the existing "escalate to a stronger model" override path in ADR-0015. Two of the skill's five primary-source URLs (`docs.claude.com/...`) permanently redirect (301) to `platform.claude.com/...`; fixed in this run per the skill's own instructions.

## Needs a human

- **Where `fable` fits (TODO.md "Models" item).** No change to `models.json` proposed. Anthropic's own guidance is explicit: "Use Claude Fable 5.1 for demanding reasoning and long-horizon agentic work, **or when your evals on Claude Opus 5.5 at higher effort still fall short**" (models overview page). That is an escalation condition, not a task-type default — none of the nine current task types are defined as "opus already tried and insufficient." ADR-0015 already has the right mechanism for this: "If a task agent reports that its task is bigger or riskier than expected, hand it to a stronger model rather than retrying on the same one." Proposal: no `models.json` edit; instead, consider naming `fable` explicitly as that escalation target the next time ADR-0015 or `renderRoutingContext` (in `plugins/factory/scripts/models.ts`) is touched, e.g. adding a line such as "When even `opus` at `high`/`xhigh` effort isn't enough, override to `fable`." This is a documentation/wording decision, not a routing-table change, so it's left for the owner to decide where (ADR text vs. `renderRoutingContext` vs. task-agent template) rather than proposed as a diff here.
- **No other `models.json`, `models.ts`, or accepted-alias/effort changes are proposed.** Every current assignment checked out against the primary sources (see Findings #2–#6). If the owner wants to act on Finding #2 (Haiku's unsupported effort) or Finding #5 (Opus's narrower price gap and "default for most workloads" framing) anyway, both are stylistic/cost trade-offs rather than correctness issues, so no JSON diff is proposed unless the owner asks for one.

## Not checked

- **Effort-support claims for `sonnet` beyond what two sources gave inconsistently.** `https://platform.claude.com/docs/en/about-claude/models/overview` lists Claude Sonnet 5.5's default effort as `high`, while `https://code.claude.com/docs/en/model-config` lists it as `medium` ("Opus 5.5, Sonnet 5.5 ... Default effort: `medium`" vs. the overview table's `high`). I could not reconcile this discrepancy between the two official pages within this run, and didn't find a third source to break the tie. It doesn't affect any `models.json` entry — `code` and `checkup` set `sonnet`'s effort explicitly (`medium` and `high` respectively), overriding whichever default is correct — but it's worth a maintainer of the docs.claude.com/platform.claude.com pages fixing, or worth re-checking on the next run.

Not checked further because they are not exposed as Claude Code aliases (the `model-config` page's alias table has no `mythos` alias), so they're out of scope for `plugins/factory/models.json`.
- **Amazon Bedrock / Google Cloud / Microsoft Foundry-specific model IDs and lifecycle dates.** Out of scope: this plugin runs through Claude Code, which resolves aliases per-provider automatically (per `code.claude.com/docs/en/model-config`'s "Model Alias Resolution by Provider" table); the checkup only needs the alias-level behavior, which was checked.

I relied on the documented behavior and ADR-0014's own anticipated consequence rather than an empirical test, since running a live task-agent invocation to observe the effect wasn't part of this checkup's scope.
