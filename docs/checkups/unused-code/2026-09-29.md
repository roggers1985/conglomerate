## About this checkup

- The scope's third bullet — "exports used only inside their own module (make them internal…) or only by tests" — is hard to apply mechanically here, because this repository's entry-point scripts (`checkups.ts`, `doctest.ts`, `session-start.ts`, `validate-plugin.ts`, `skills.ts`, `agents.ts`) deliberately export nearly every internal helper function and type. That's not an oversight: `bun run doctest` (ADR 0016) only checks *exported* declarations for TSDoc and a tested `@example`, and the project's own `test-coverage` checkup report (2026-09-29) already praised these scripts' pattern of unit-testing helpers directly and covering the CLI path via a subprocess test. A naive read of the scope bullet would flag dozens of these exports (e.g. `buildReminder`, `parseSchedule`, `ExportKind`, `SessionStartOutput`) as "used only inside their own module or only by tests" and suggest un-exporting them — but doing so would silently exempt them from the doctest/TSDoc requirement and contradict the accepted, working convention. I only applied the bullet to `lib/predicates.ts`, a genuine shared-lib module with zero consumers anywhere (not even indirectly through an exported, externally-used function), and left the entry-point scripts' internal-but-exported helpers alone. It would help future runs to say explicitly in the skill that this "export for testability/doctest" pattern in entry-point scripts is exempt, so as not to re-litigate it every run.
