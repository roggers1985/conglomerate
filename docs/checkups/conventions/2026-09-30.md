# Checkup: conventions (2026-09-30)

Model: Claude Sonnet 5.5
Previous report: none (first run)

## Summary

The conventions are in good shape and their sources have barely moved: TigerStyle's last real change is from February 2026, Power of 10 and "Parse, don't validate" are unchanged, and the only moved URL was Biome's rule list (corrected in the skill). The most important finding is a gap rather than a change: the `code-react` skill cites React's rules and "You Might Not Need an Effect" as its sources but contains none of their substance, while the `frontend-quality` checkup already judges code by them, so the rule is enforced on code that was never told about it. Besides that there are six small contradictions between rules and the examples or code that illustrate them, one rule that is too strict for long-running loops (Power of 10 itself has the exception), and three Biome rules that enforce existing conventions and report nothing in this repository today. Nothing in this report has been applied; every change needs the owner's decision and an ADR.

## Needs a human

Every proposal below is a change to a convention or to the lint configuration. Together they could be one ADR ("Conventions checkup, first round") that extends ADR 0032 (P1), ADR 0038 (P5 to P7) and ADR 0008 (P2, P3) and does not contradict any accepted ADR. The order is by value.

**P1. Loops that are meant to run until cancelled** (finding 2). Source: Power of 10 rule 2 rationale; TigerStyle "Safety". Bug prevented: a fake counter that stops a healthy worker after N iterations, or a rule everybody learns to ignore. Fits: lead by logic (the source's own reason), no new surface. Where: `code-safety` "Loops", replacing the line "No `while (true)` without such a counter." Needs: a new ADR that extends ADR 0032 (its text must not be rewritten). Text:

> - No `while (true)` without such a counter, with one exception: a loop that is meant to run until it is cancelled (a worker, a poller, an event loop). Power of 10 turns the rule around for these: it must be provable that the loop cannot end by itself. Its condition is the cancellation signal (`while (!signal.aborted)`), so cancellation is the only way out, and each iteration does bounded work.

**P2. Fill `code-react` from its sources** (finding 1). Source: react.dev "You Might Not Need an Effect", "Rules of React", React Compiler 1.0. Bug prevented: extra renders and stale or out-of-sync state from effect-driven derived state, the main source of React bugs; it is the rule `frontend-quality` already checks. Where: `code-react` (and `core.md` needs nothing, since the skill loads for React work). Needs: a new ADR (none exists for `code-react`). Suggested text, to add after the existing four bullets:

> - **Derive, don't sync.** A value that can be calculated from props and state is calculated during render; it is never copied into state and kept in step by an effect. Reset state by giving the component a `key`, not with an effect.
> - **Events belong in event handlers.** Logic that runs because the user did something (including notifying a parent component) lives in the handler, not in an effect that watches state.
> - **Effects synchronise with something outside React** (subscriptions, timers, non-React widgets, client-only fetching), and clean up after themselves (see `code-cancellation`). Use `useSyncExternalStore` for external stores, and `useEffectEvent` to read the latest values in an effect without re-running it.
> - **Components and hooks are pure:** no side effects, and no mutation of props, state or hook arguments, during render. Hooks are called at the top level only.
> - **In a project with the React Compiler, no manual `useMemo`, `useCallback` or `memo`** unless a measurement or a stable effect dependency needs it.

Enforcement: Biome's React-domain rules `useExhaustiveDependencies` and `useHookAtTopLevel`, and `noReactForwardRef` (for the existing "no `forwardRef`" line), exist in Biome 2.5.14. The compiler's `set-state-in-effect` lint has no Biome equivalent; whether a React project adds `eslint-plugin-react-hooks` next to Biome is a decision for when there is a React project (hand to `new-features`). Not proposed now: `use(browser())` from 19.3 (three weeks old; look again next time).

**P3. Web-first assertions in `code-testing`.** Source: Playwright best practices ("Use web first assertions"). Bug prevented: a flaky test (`expect(await locator.isVisible()).toBe(true)` checks once and does not wait; `await expect(locator).toBeVisible()` retries), and `code-testing` already calls a flaky test a bug. Where: `code-testing` "End-to-end tests", one line after the `getByRole` line. Needs: fits under ADR 0031 (a short amending line in the new ADR). Text:

> - Assert with Playwright's web-first assertions (`await expect(locator).toBeVisible()`), never on a value you read first (`expect(await locator.isVisible()).toBe(true)`): the former waits and retries, the latter checks once.

Enforcement: Biome has `noPlaywrightWaitForTimeout`, `noPlaywrightForceOption` and `noPlaywrightElementHandle` (nursery), which enforce "never `waitForTimeout`" and related rules as soon as the repo or a project has Playwright tests (hand to `new-features`). No Biome rule for web-first assertions exists.

**P4. Turn on three rules that enforce existing conventions.** Sources: TigerStyle/ADR 0038 ("all errors handled"), the checkup protocol and `code-testing` ("never skip a test"). Tested here: zero reports on the current 45 files; each catches its case in a sample. Where: `biome.json`, under `linter.rules.suspicious`. Needs: an amendment sentence in ADR 0038, which says three rules were added and names them. Text:

```json
"suspicious": {
    "noEmptyBlockStatements": "error",
    "noSkippedTests": "error",
    "noFocusedTests": "error"
}
```

`code-safety` "Errors" should then also name `noEmptyBlockStatements` next to the promise rules. Also tried and rejected: `noMagicNumbers` (the "no bare numbers in conditions" rule) reports 68 times, 51 in tests and 17 in source files, where it flags the arithmetic inside named constants (`const DAY_MS = 24 * 60 * 60 * 1000`) and schema bounds (`.max(100)`), which are exactly the named, documented numbers the convention asks for, so it would push toward noise. `noShadow` and `useErrorCause` also report nothing, but no convention asks for them.

**P5. Keep branching in the parent when splitting a function.** Source: TigerStyle ("push `if`s up and `for`s down", "keep leaf functions pure"). Bug prevented: control flow spread over helpers that each change state, which is what makes a long function hard to split and to test. Fits: declarative by default (pure steps), readability. Where: `code-safety` "Functions", one sentence after "split where it has a name for a part". Needs: the new ADR. Text:

> When splitting, keep the branching (`if`, `switch`) in the parent function and move the work that doesn't branch into helpers; helpers that only compute stay pure, and the parent applies the result.

**P6. Split compound assertions.** Source: TigerStyle ("prefer `assert(a); assert(b);` over `assert(a and b);`"). Bug prevented: a failure that names neither condition. It is "one condition per `if`" applied to `assert`, so it adds no new idea. Where: `code-safety` "Assertions", as a bullet. Needs: the new ADR. Text:

> - **One condition per `assert`:** `assert(start >= 0, "start is negative"); assert(start <= end, "start is after end");` rather than `assert(start >= 0 && start <= end, …)`, so the failure says which one broke.

**P7 (thin, optional). Assertions before an `await` do not hold after it.** Source: TigerStyle ("ensure that functions run to completion without suspending, so that precondition assertions are true throughout the lifetime of the function"). Bug prevented: a check-then-act race between an `await` and its use (a cache entry, a queue, a counter). Only matters in concurrent code, which this repository has little of, so the owner may prefer to wait for a project that needs it. Where: `code-safety` "Assertions", one line:

> - State that other code can change (a cache, a queue, a counter) is re-checked after an `await`; an assertion made before it says nothing about after it.

**P8. Make the skills' examples follow their rules** (finding 4). Changes to three examples, no rule changes: in `code-safety`, `body: z.string().min(1).max(10_000)` becomes a not-blank check (a `.refine((text) => text.trim().length > 0, "is required")` or a shared helper such as this repo's `requiredText`, which `code-parsing` could mention as the pattern); in `code-cancellation` and `code-documentation`, `fetchJob` names its timeout (`const FETCH_TIMEOUT_MS = 10_000; // …`) and either takes it as an option or says in the `@remarks` why it is fixed, and reads the body with a size bound; in `code-accessibility`, the `color-contrast` exclusion is named as the one allowed exception ("jsdom can't compute colour contrast; the page-level scan covers it"), by adding that sentence to the Rules. Needs: no ADR (it only makes examples match existing accepted rules).

**P9. Sharpen `code-api-design` section 2** (finding 5). The repository's own code, the skills' examples and the owner's own `readText`/`readJson` all return bare values from operations that throw on failure. Recommendation: change the rule, not the code. Suggested text for the bullet "The result of an operation …":

> - **The result of an operation that reports an expected outcome as data** (parse, validate, anything that can partly fail, or whose callers branch on the outcome) is an **object or a discriminated union**, never a bare value. An operation that either returns its one value or throws (reading a file, fetching one record) may return the value itself.

Needs: a short amendment to ADR 0017 in the new ADR (ADR 0017 is accepted, so the change goes in a new record that extends it).

**P10. Two wording fixes against primary sources** (findings 6 and 7). `core.md` "Licenses": add ", EPL" to the copyleft list and the sentence "For an SPDX expression, `A OR B` needs one allowed side, `A AND B` needs both (ADR 0035)." `code-sql`: replace "so a column only accepts its declared type" with "so a column only accepts its declared type (values are still converted by the usual affinity rules where the conversion is lossless; never declare a column `ANY`)", and in "Keys and relations" add "In PostgreSQL 18 and later, `DEFAULT uuidv7()` generates it in the database." The two sources are the SQLite STRICT documentation and the PostgreSQL 18 release notes. Needs: no ADR for the wording; the `uuidv7()` line could be left until a project needs it.

Considered and not proposed, to keep the surface small: commit messages must say why (TigerStyle's 2026-02 change): the repository's commits already do, and adding a rule only adds a sentence to `core.md` for behaviour that already happens. `noUnnecessaryConditions`: still off, the `new-features` report re-confirmed the false positive yesterday. A Biome GritQL plugin that flags `&&`/`||` inside an `if` condition (the "one condition per `if`" rule is the only central rule that is enforced by review alone): Biome 2.5 supports plugins, but guards like `if (!a || !b)` exist in the code on purpose, so a plugin would need exceptions; leave it to `new-features` if the owner wants it. `using` declarations for cleanup: not Baseline. PostgreSQL 18 temporal constraints (`WITHOUT OVERLAPS`): applies too rarely to earn a line.
