# Checkup: new-features (2026-09-29)

Model: Claude Sonnet 5
Previous report: none (first run)

## Summary

First run: inventory is Bun 1.4.2, TypeScript 7.0.2 (native/Go compiler, GA July 2026), Biome 2.5.14 and Zod 4.6.5, all already at latest (confirmed against today's `outdated-packages` report). None of their last-year's worth of new features gave a clear, behaviour-preserving win in this ~3,200-line codebase — `code-quality`'s report run today already found it idiomatic and duplication-free. The most useful finding is a re-verification, not a new discovery: Biome 2.5's `noUnnecessaryConditions` (promoted from nursery to `suspicious` in this release) still produces exactly the false positive ADR 0019 described — it treats `RegExp.prototype.exec()` as never returning `null` — on all three call sites in this repo (`scripts/skills.ts`, `plugins/factory/scripts/doctest.ts`, `plugins/factory/scripts/checkups.ts`). The rule stays off. No code changes were made this run.

## Not checked

- Bun 1.4's new `Bun.WebView`, `Bun.Image`, `Bun.markdown`, JSON5/JSONL, and cron APIs were considered against this repo's regex-based frontmatter/fence scanners (`scripts/skills.ts`, `plugins/factory/scripts/doctest.ts`) and `checkups.ts`'s interval math, and rejected: those scanners are deliberately narrow, single-purpose parsers documented as such ("A deliberately small, regex-based scanner"), not general Markdown, and there is no long-running process for a cron API to schedule against (checkups run once per session-start invocation). Reaching for a heavier dependency there would be scope creep against an explicit design choice, not a "clear win."

## About this checkup

- The skill's scope point 5 ("is the choice still the recommended one? Report only; changing it is a decision") reads as being specifically about ADR 0020's Zod choice, but the phrasing ("the schema library **and other deliberate choices**") suggests it wants every ADR's "for now"/"revisit later" choice surveyed, not just Zod's. This run treated ADR 0019's `noUnnecessaryConditions` note the same way (it's exactly this pattern — a rule turned off "for now" pending a checkup revisit) even though it lives in "Settings and rules" (point 4) rather than point 5. Worth clarifying in the skill whether "deliberate choices recorded in ADRs" is meant to be read broadly across all ADRs each run, or narrowly as "point 5 covers only the schema library, point 4 covers only lint/type settings" — they overlapped naturally here, but a codebase with more ADR footnotes could make the boundary matter.
- Everything else (branch naming, generated-files list, the check command, the report template) matched the repository exactly; no friction.
