# Checkup: claude-code-platform (2026-09-29)

Model: Claude Sonnet 5
Previous report: none (first run)

## Summary

The factory plugin's manifests, hooks, skill/agent frontmatter and `claude plugin validate` are all current against Claude Code 2.1.284's documented platform (no deprecated fields, no compatibility issues, `bun run check` and `claude plugin validate plugins/factory` both pass clean). The most important finding answers the open TODO question directly from the docs: for this repository's install (a relative-path plugin inside a marketplace added from a **local directory**), the plugin **loads in place from its live source files at every session start or `/reload-plugins`, regardless of `version` in `plugin.json`** — so `claude plugin update factory@conglomerate` is not what makes edits visible, and bumping `version` is not required. GitHub Copilot now has its own Agent Skills feature (`SKILL.md`, discovered from `.github/skills/`, `.claude/skills/`, or `.agents/skills/`), but it cannot see the factory plugin's skills as installed, because they live inside the plugin package rather than directly in one of those repo directories.

## Needs a human

- **Record the TODO answer** (finding #1): the docs confirm that for this repo's local-marketplace, relative-path install, the plugin loads live source at every session start / `/reload-plugins`, independent of `version`. Proposed text for `CLAUDE.md`'s installation line (replacing/annotating the current "After changes: commit, then `claude plugin marketplace update conglomerate && claude plugin update factory@conglomerate`, and restart sessions"):
  > After changes: commit, then restart Claude Code sessions (or run `/reload-plugins`). `claude plugin marketplace update` / `claude plugin update` are unnecessary no-ops for this local, in-place install — the plugin always loads its current source files regardless of `version` in `plugin.json`.
  Once recorded, the matching TODO.md item ("Verify how updates reach the installed plugin…") can be removed.
- **ADR-0024's "Updating after changes" steps** (finding #2) are accepted-decision text and can't be hand-edited per the checkup protocol's hard rules (only status/links may be corrected). If the owner wants the documented procedure to match what's actually needed, that's a small superseding ADR (e.g. "0025: simplify the local-marketplace update procedure") — proposal: drop the `claude plugin marketplace update` / `claude plugin update` steps, keep commit + restart/`/reload-plugins`. Not done here since it changes a decision record and the checkup may only add a superseding record's proposal, not the record itself.
- **Copilot skill compatibility** (finding #3): if the owner wants Copilot to run the factory's skills, that needs a distribution decision — e.g. a `bun run generate` step that copies/symlinks each skill's `SKILL.md` into `.github/skills/<name>/` (or `.agents/skills/`) in a consuming project, trimmed to the six-field agentskills.io spec (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools` — dropping Claude Code-only extensions like `argument-hint`, and checking whether the runner skill's `` !`command` `` dynamic-context injection has any Copilot equivalent, which wasn't verified). This is a structural change to the plugin (ADR-0002 already deferred Copilot support) and needs its own ADR; not built here per the checkup's scope ("Report what would be needed; don't build it").
