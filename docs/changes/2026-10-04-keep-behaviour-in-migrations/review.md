# Review: Keep behaviour the same during a migration

## Summary

The change does what the spec says. All eight criteria are met, their evidence holds, the named tests pass, and `bun run check` passes (492 tests, 101 doctest examples). The gate code is small and reads `migration-plan.md` through the existing change-document reader, which is bounded and refuses symbolic links (ADR 0060).

What matters most: the skills don't yet say exactly what "unchanged" means for the behaviour test. Read literally, the review's new check flags every side-by-side migration and every intended difference, and it misses a re-recorded golden master (findings 1 and 2). The build and review rules also don't fit a schema-only migration or the quick track, and planning doesn't make the behaviour test the first task (findings 3 to 5). None of these breaks a criterion; they are gaps in the text that a real migration would hit.

## Findings

| # | Severity | Finding | Where | Status |
| - | -------- | ------- | ----- | ------ |
| 1 | medium | "Unchanged" isn't defined, and the texts contradict each other. Side by side, the first task can only list the old version, because the new code doesn't exist yet. Adding the new version later changes the test file, and so does removing the old one ("When the old code goes, its entry goes"). In place, an intended difference can't pass on the old code, so its assertion must change at the swap, yet `code-testing` says "the swap leaves the test file unchanged". The review diffs the whole file, so it would raise a high finding on every legitimate side-by-side migration. Recommendation: define it once in `code-testing`. The test cases and their expectations stay unchanged. The only allowed edits are adding or removing a version in the side-by-side list, and the assertions for the intended differences the spec lists. Let the review's point 7 and ADR 0062 refer to that definition. | `plugins/factory/skills/code-testing/SKILL.md` ("Two forms", "In place"); `plugins/factory/skills/factory-review/SKILL.md` point 7; ADR 0062 Decision | open |
| 2 | medium | The review diffs only "the test file". A golden master is also part of the proof. Re-recording it from the new code makes the test pass whatever the new code does, and the review wouldn't see it. A behaviour test can also span several files. Recommendation: point 7 diffs every file of the behaviour test, including recorded outputs, and the migration plan's Behaviour test section names those files. | `plugins/factory/skills/factory-review/SKILL.md` point 7; the migration plan template in `plugins/factory/skills/factory-planning/SKILL.md` | open |
| 3 | medium | A schema-only migration fits the template, but not the build and review rules. Both trigger on "when the route has a migration plan". The build then asks the first task to write "the behaviour test the plan names" and run it on the old code, and the review asks to diff "the test file". A schema-only plan names a data check, such as row counts and checksums before and after, which may not be a test file at all. A reviewer following point 7 literally would raise a high finding. Recommendation: say in the build skill and in point 7 what applies to a data check. The check the plan names runs before and after each step, `verification.md` records both results, and the diff check applies only when the plan names a test. | `plugins/factory/skills/factory-build/SKILL.md` ("When the route has a migration plan"); `plugins/factory/skills/factory-review/SKILL.md` point 7 | open |
| 4 | medium | Planning doesn't put the behaviour test first. The build says "the first task writes the behaviour test", but the planner writes the task list, and `factory-planning`'s tasks section says nothing about it. A planner following the skill can make T-1 something else, or mark other tasks `Parallel: yes` so they run alongside it, before the test has run on the old code (AC-6: "before any task changes the code under test"). Recommendation: in the tasks section, when the route has a migration plan, T-1 writes the behaviour test and runs it on the old code, and every task that changes the code under test depends on T-1. | `plugins/factory/skills/factory-planning/SKILL.md`, "The tasks stage" | open |
| 5 | medium | The quick track has no answer. A small library swap is small, low risk, reversible and low uncertainty, so triage routes it as quick and adds `+ migration-plan`. But the quick track has no change folder, so it has no `migration-plan.md` and no `verification.md` to record the run on the old code. The review's point 7 then has nothing to read. Recommendation: on the quick track, there is no migration plan document. The build still writes the behaviour test first and runs it on the old code, and the reply and pull request record that run, as they do for evidence. The review checks it there. The other option is that `+ migration-plan` always means at least the standard track. | `plugins/factory/skills/factory-triage/SKILL.md` ("+ migration-plan"); `plugins/factory/skills/factory-build/SKILL.md` (quick track) | open |
| 6 | medium | The planning gate promises a check the code doesn't do for the migration plan. Step 4 of "The gate" says the route check refuses a done stage with an open `[NEEDS CLARIFICATION]`, and step 2 asks the planner to use that marker. `migrationPlanProblems` only checks sections, so a done migration plan with an open question passes. That matters here: a step that can't be rolled back needs the owner's explicit approval. Recommendation: add `clarificationProblems` to `migrationPlanProblems`, as `planProblems` does, with a test. The other option is to say in the skill that the migration plan's gate checks only its sections. | `plugins/factory/scripts/stage-gates.ts` (`migrationPlanProblems`); `plugins/factory/skills/factory-planning/SKILL.md`, "The gate" | open |
| 7 | low | The template doesn't prompt for the case where the test framework itself is migrated. The spec's edge case says "The migration plan says so (AC-4)", and `code-testing` and the ADR describe it, but the Behaviour test section doesn't ask for the level the test moves to. Recommendation: add a fourth bullet to that section, the level the test runs at when the test framework itself is migrated. | `plugins/factory/skills/factory-planning/SKILL.md`, the migration plan template | open |
| 8 | low | For an in-place swap, the section "Old and new side by side" must say that nothing runs side by side ("the old code is replaced in place in one step"). The template allows it, but the heading reads oddly. Recommendation: rename it "Old and new", or "How old and new coexist", in the template, `MIGRATION_PLAN_SECTIONS`, ADR 0062 and AC-4. Or keep it and accept the wording. | `plugins/factory/scripts/stage-gates.ts` (`MIGRATION_PLAN_SECTIONS`); the migration plan template | open |
| 9 | low | The name `investigationProblems` fits the spike, but a migration plan isn't an investigation. Its comment says what it really groups: stages that write one document with required sections. Recommendation: a name like `sectionedDocumentProblems`. | `plugins/factory/scripts/changes.ts:293` | open |
| 10 | low | Triage's Reversible row lists "migrations" as not reversible. "Migration" now also means a code migration, such as a library swap, which usually is reversible. Read literally, the row sends every code migration to the full track. Recommendation: write "schema and data migrations" in that row. | `plugins/factory/skills/factory-triage/SKILL.md`, the classification table | open |
| 11 | low | Criterion ids in test names now come from different changes. `skill-templates.test.ts` has "AC-5: …" tests from the writing change, next to this change's "AC-4: …" test. `changes.test.ts` has "AC-7: refuses a done stage whose document fails its gate" from the pull request change, next to this change's AC-5 tests, while this change's AC-7 is the review check. The evidence itself is sound: `verification.md` names the file and the full test name, which are unique. The id alone, though, no longer says which spec it belongs to. A reader can't tell, a builder could cite an older test with the same id, and the evidence script in TODO.md ("names its criterion") would accept either. Recommendation: not in this change, because it changes ADR 0054's naming rule. Add a TODO item to qualify the id with the change's short name in new test names (for example `it("migrations AC-5: …")`), and leave existing tests as they are, since renaming them would break their changes' evidence. | `scripts/skill-templates.test.ts`; `plugins/factory/scripts/changes.test.ts`; `plugins/factory/skills/factory-build/SKILL.md` step 3 | open |
